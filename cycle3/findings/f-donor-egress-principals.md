# Publish a coherent donor provider-proxy and credential-refresh network owner

- **Lens:** remote-worker adversarial review; network and credential ownership.
- **Problem:** Donor variant B permits the model-provider proxy to run under the bridge identity while its mandatory per-UID policy permits that identity to reach only the project SSH host and join endpoint. The bridge-UID proxy therefore cannot serve the provider request that the harness is expressly required to send through it. Calling the proxy a system service does not repair this if it retains the same UID. A separate service-account option can work, but the donor contract does not assign its egress or reconcile the bridge-owned credential node and Codex refresh path. This is a definite contract contradiction in a gated design, not an observed deployed failure. Variant B correctly remains disabled pending its provisioner specification and qualification.
- **Evidence:**
  - `curator-spec` at `a0154285`, `cips/CIP-0009-donor-side-deployment-and-bridge.md`, D1 lines 127–128: harness egress is to the provider proxy only; bridge egress is to project SSH/join only; the provider proxy may run as the bridge identity or a system service. D2 line 136 repeats the per-UID SSH/join-only bridge policy.
  - Same revision, `cips/diagrams/donor-side.dsl` lines 34–35 and 65–66, `cips/diagrams/donor-variants.puml` lines 16, 43 and 48, and `cips/diagrams/donor-layout.puml` line 22 retain the incompatible proxy placement and network path.
  - Same revision, `cips/CIP-0010-credentials-setup-token-and-inherited-auth.md`, C2 line 105 and C5 line 124: the donor needs one Codex auth owner, while the credential node and supervisor lookup belong to the bridge identity. Neither section supplies a separately authorized donor login/refresh route.
  - `curator-network-profiles-dev` at `359365e`, `spec/network-profiles.md`, N15 lines 192–194: the platform-host proxy and broker have explicit service/listener ownership, including observed vendor login/refresh destinations. These platform-host rows do not grant donor-B bridge egress; CIP-0009 D-DONOR-PROVISIONING deliberately separates donor provisioning.
- **Proposed change:** Publish one donor principal-and-route table covering the harness, bridge, provider proxy and credential login/refresh owner. Make the chosen provider-egress service principal explicit. Preserve the bridge's SSH/join-only policy by assigning provider dialing to a separate principal and specifying any required authenticated local credential-owner access; alternatively, any deliberately combined authority must be stated, reviewed and qualified as such. Remove the contradictory bridge-UID option unless its network policy is deliberately reconciled. Update CIP-0009, CIP-0010, the shared remote-worker contract and affected figures together. Keep variant B disabled until the selected ownership, provisioning/removal and real provider/refresh paths are qualified; donor credentials stay donor-side.
- **Expected benefit:** An implementable donor B network boundary, with inference and credential renewal both accounted for. Prevents implementers from discovering an impossible route late and silently broadening the signer/bridge's network authority to make it work.
- **Risks and costs:** A separate provider-egress principal may add donor provisioning and local IPC configuration. A combined principal increases authority and needs an explicit review. This finding does not select a new wire schema, alter project-host N15, move donor credentials to the project, or challenge the owner-approved A/B/C deployment order. The separate Codex loopback control path is not claimed as peer-confirmed by this finding.
- **Affected specs:** curator-spec CIP-0009 D1/D2/D5, CIP-0010 C2/C5, `protocol/remote-worker.md`, donor deployment/component/layout figures and the future donor-provisioner contract.
