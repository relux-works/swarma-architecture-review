# R-TRANSFER's landing, pending-ref publication and verification handoff have no network principal under R-NET-TOOL

- **Lens:** trust and threat model (fable); shared consistency lens. R-TRANSFER (astra-15), user manager (astra-12) and book/decisions (wonder-12) cross-checks.
- **Status:** proposed.

## Problem

Two owner decisions of 2026-10-13 do not compose as written. R-TRANSFER has the orchestrator execute import, candidate, review and integration: "The accepted exact head integrates by signed fast-forward (K1/K3)"; the board draft publishes an unaccepted C to a pending ref namespace at the repository host so that no CI runs it, and hands a self-contained bundle of C over B to the off-host verification runners. R-NET-TOOL and N15 give the orchestrator's account no route to any of these: a trusted local agent's profile admits only the model-provider endpoints of its qualified tuple, and no agent profile lists a package registry; the dispatcher and the session host deny all egress; the broker reaches only its vendor listener; the web-tool service serves ports 80 and 443 to opted-in search. The trust contract's privilege table has no row for a repository transport or landing service, and VISION item O1 leaves "shared-main landing coordination" outside the platform. The board's live landing route is a PR branch at the hosting provider closed with `close-landed` from a checkout, which is a push by the principal running the CLI. Under enforcement that principal, the orchestrator, cannot push, fetch a moved base, publish a pending ref or deliver a bundle; under R-TRANSFER no worker may. Steps 5 to 8 of the decided path and the R-VERIFY handoff therefore have no published network owner. The book narrates the same path with the same gap: the orchestrator moves the accepted candidate by signed fast-forward, and the chapter-3 service table lists keeper, user manager, launcher, broker, dispatcher, session host, operator, observer, proxy, runner and bridge, with no repository-transport row.

The gap appears only under platform enforcement; today's board landing runs in the same-account world, and local import and a local fast-forward remain possible. The platform already knows the question exists: the trust contract gates cross-account workspace launches on publishing "who transfers source and results", and the board draft leaves bundle transport open in its own implementation plan. What is missing is the owner, the egress and the authority of that publication. `f-book-egress-example` removes the book's code-hosting example from agent egress; this finding is its complement: once code hosting leaves agent profiles, which principal reaches it.

**Trust reading.** This is the right outcome, not an accident to undo. The repository host is an external party, and the platform's pattern for external parties is a service principal: the bridge for the carrier, the proxy for the model provider; an agent never holds the credential or the route. What is missing is the name of that service and the placement of the checks where the action is performed (book chapter 5: grants are checked where the action is done). If a service pushes on the orchestrator's request, the service itself must verify the verdict's binding to exact C and the signed non-forced fast-forward; otherwise a prompt-injected orchestrator can ask it to push anything, and the trunk's write authority would have moved from an agent account to a service that trusts the agent.

## Proposed change

1. **Name a repository-transport principal.** A non-agent capability boundary with its own N15 service row (the repository host and the runner-pool ingress, through the proxy with served-policy evidence, as the broker does), listed in the trust contract's privilege table, N15 item 7 and the book's service table. Its topology and custody are an owner choice, not inferred from the carrier rule: a qualified existing trusted actor (the board's control plane), a dedicated `swarma-landing` service, off-host trusted artifact transfer, or an explicit initial operator-mediated lane. Whatever performs the external effect holds the credential and enforces the authority; no agent account holds a repository credential or a route to the host, and the board server is not revived by this finding.
2. **Three registered actions, verified at the service.** Publish-pending: push exact C to the pending namespace only after the import's hard refusals and the CI-free qualification. Hand-off: the digest-addressed bundle of C over B plus the approved harness revision H to the runner pool. Land: a signed, non-forced fast-forward of exactly C to the protected ref, only with a verdict record bound to C's commit OID and a fresh re-resolution of the protected ref (K1/K3). The orchestrator requests them through the board client under its grant; the service re-checks the grant chain and the verdict itself. The repository signing key lives with the keeper or the service, never in an agent home.
3. **Base refresh** and re-review fetch through the same service; the orchestrator's repository is fed from it, never from the host directly.
4. **Deployment.** On a host admitting untrusted work the service is platform-owned (R-SHARED excludes shared services, not platform services); its row is re-verified like every service row (R-SVC-EGRESS).
5. **Qualification, per action.** An orchestrator account cannot reach the repository host or the runner ingress. Publish-pending refuses without a board-built C from the deterministic import and without the pre-qualified CI-free namespace (it precedes acceptance by design). Hand-off binds to the C, B, H and artifact identities. Landing refuses without a verdict record bound to C's OID, refuses a moved protected ref, and never rewrites or forces. Each check is enforced at the effect boundary, never asserted only by the requesting agent.
6. **Book and VISION.** Chapter 12 and the chapter-3 table gain the row together with the spec fix; VISION O1 stays true for coordination (windows, arbitration), not for transport.

## Expected benefit

The decided path becomes executable under enforcement. Write authority over the trunk moves from an agent account to a service that verifies K1/K3 itself, and the repository credential leaves agent reach; one more external-party route follows the bridge and proxy pattern.

## Risks and costs

A new service row and a small action contract; the board's live `close-landed` route changes shape, which is a visible change to today's workflow; N15 gains a row. No owner decision is challenged; the finding reconciles two decisions of the same day.
