# Align initial v1 provisioning with the user manager's enforced activation boundary

- **Lens:** dispatcher admission and effects; cross-module creation and network activation.
- **Problem:** The trusted v1 provisioning path gives two incompatible orders for initial enforcement. The dispatcher calls `user.create`, receives the created generation, and then issues a separate `fw.apply`. The user manager's successful `user.create` result is already `active`, but its network contract requires verified per-account enforcement, applied-state publication and that account activation to commit together. Its own creation figure places enforcement before the active result.

  If the dispatcher follows its sequence and creation has the documented successful result, the generation is already active before the apply that must accompany activation. If creation waits for the separate apply, the caller has not yet reached that step. No prepared-generation handoff reconciles these descriptions. Dispatcher allocation state `provisioning` is not a different definition of helper account state `active`.

  This is an initial-activation call-order and ownership defect, not a demonstrated deadlock or unfiltered launch. The static range deny precedes accounts, every physical start checks current network gates, and the dispatcher does not finish provisioning before its effects complete. The v1 formats remain gated. A missing wire member alone is not the finding: the already stated result, commit boundary and inter-service sequence disagree.

- **Proposed change:** Select and publish one initial-enforcement ownership and handoff, then align both specifications and figures.
  1. A direction that preserves the current successful-create boundary is for creation to own initial enforcement, with an admitted immutable policy context and an explicit generation/listener handoff before the active result. Define how initial enforcement evidence and journal/effect identities link to the create effect. Keep separate `fw.apply` for existing-allocation re-apply. Do not infer additional helper authority to provision a proxy from its permission to query listener evidence; publish the selected owners.
  2. If a staged design is selected instead, define the non-launchable prepared-generation result, its observation and recovery semantics, the separate apply/activation commit, and abandonment/rollback. It cannot simply reuse the current unfinished-creation row: the next dependent operation currently rolls interrupted creation back. No new state spelling or operation name is proposed by this review.
  3. In either design preserve the exact admitted pin and listener-generation evidence, distinct/replay-safe effects, account reservations, existing creation rollback guarantees and unlocked cross-service I/O. Neither launch nor workplace ingress may become admissible before verified enforcement. A helper `active` result and dispatcher completion must describe the selected boundary consistently; v0 behavior must remain clearly separated.
  4. Qualify the initial happy path and crashes before/after generation assignment, listener preparation, applied-state publication, account activation and caller acknowledgement. Include failed/unavailable listener evidence, a delayed duplicate create/apply, policy drift, rollback and standing-team retry without duplicate allocation. Retain existing late-result, ALLSTOP and retirement fences.
- **Expected benefit:** Initial trusted v1 provisioning has one implementable activation boundary. Its effect results and recovery evidence agree across the caller and receiver, without weakening the before-activation enforcement rule or introducing an implicit prepared state.
- **Risks and costs:** Joint publication of the selected initial handoff and effect ownership, plus figure and qualification updates. A staged design adds recovery states and abandonment semantics; a create-owned design must explicitly obtain admitted policy and generation-specific listener evidence. No new service, wire field, state spelling or operator decision is invented here. F-27's pinned policy and F-28's lock discipline remain requirements.
- **Affected specs:** dispatcher §5.1, §5.5, effect/observation references and `dispatch-lifecycle.puml`/`bring-up-team.puml`; user manager §§4.2–4.3, 4.6, 8, 12, 14 and `provision-retire-recovery.puml`; N15 initial listener handoff where the selected design needs it.
