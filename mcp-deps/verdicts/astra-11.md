## Preferred design and minimum delta

Prefer **N**. The owner's stated need already has a portable declaration: `dependencies.mcp_servers`. The missing bridge is dependable satisfaction across provisioners and launch modes, not another recipe identity in each skill.

1. Remove `server` from the mandatory direction. Keep skill requirements as `{hint, transport?, required_in?}`; `transport` remains documentary under the existing contract.
2. Define selected-scope evidence in manager §6: configured and enabled, observed versus operator-asserted, unknown/missing/disabled, and `any`/`all` over the original target set. No implicit dropping of unsupported targets. An assertion is authority to accept a scoped provider, not proof of a running/authenticated server.
3. Put the one provider-binding relation in protected operator state. Repository/project files may suggest a mapping, but cannot authorize or assert it. Reuse that relation for aliases; do not add a second alias graph. Its minimum binding covers requirement/skill identity, target agent, project/profile or native launch scope, selected provider, evidence kind, and invalidation on relevant change. These are semantic costs even if encoded inside one map.
4. Keep provisioning an explicit, separate plan under existing package allowlist, audit, signer and writer ownership rules. A requirement, native name, receipt, or declaration lock does not itself approve an executable or destination. Authentication stays in the native client/operator lane.
5. Do not add an `auth` class merely to print generic native-client guidance. `env_names` already expresses requested environment names; HTTP does not imply OAuth, and absence of env names does not prove `none`. If machine-readable auth changes writer behavior, propose it separately in a new declaration schema rather than silently widening schema 1.
6. Apply an explicit bounded metadata-only parsing contract to foreign configs. Never retain/report raw foreign argv, URL or env values; never copy native secrets into evidence, logs, hashes intended as portable identities, or bindings. A digest of a recipe is not package provenance.

N deliberately makes no globally registered service/capability vocabulary, MCP proxy, auth broker, or new discovery plugin API. If stronger skill-author identity is later demonstrated necessary, I is a separately versioned opt-in extension rather than a prerequisite for the user's basic goal.

## Counterexamples for the debate (not executed tests)

1. Add `server` to the shared `mcpRequirement`: a v5 manifest previously rejected becomes accepted without a new schema version. This violates the frozen-object rule even though the member is optional.
2. Two declaration packages from different repositories produce identical `npx` argv. Recipe equality cannot establish the package source identity required for allowlist/signer policy.
3. A required server is present in native `.mcp.json`, but the selected Claude managed launch actually applies `--strict-mcp-config` with a present channel file containing a non-empty, different profile set. Legacy native discovery succeeds; launch-scoped satisfaction must not. An empty profile set alone is insufficient evidence of exclusion because §5.8 emits no channel file for it.
4. A cloud connector has no inspectable local config. Counting unknown as available lies; requiring a fabricated local endpoint excludes the zoo. A visibly scoped operator assertion can support honest declared provision without claiming connectivity.
5. `agent-mcp.json` schema 1 gains `auth: oauth`. Both root and server schemas reject unknown fields today; adding it silently forks a spec-owned schema series.
6. A binding is copied from one project/profile into another, or survives a changed provider/skill identity. Global name equality must not silently preserve that asserted authority.
