# astra-01 — spec fit and minimality

Status: round 11, provisional; independent comparisons recorded, awaiting convener PARK. Author: `ivmbp_swarma-mcp-deps_astra-01` on `ivmbp`.

## Position

Prefer **named requirements plus operator-local provider evidence** (`N`, topic `alt-names-local-evidence`), optionally complemented by an inert skill-shipped declaration (`A+N`). The base's separation of requirement, provision, and operator choice is useful. Its mandatory identity interpretation of an optional `server` field adds a resolver/provenance problem that the owner's stated goal does not require. Remove that field from the core proposal, retain existing declaration packages for independently selected provisioning, and spend the new specification work on honest evidence and protected operator choices.

This is a conditional design preference supported by the independent comparisons below, including an actual cross-host pair. The rubric agreement is not implementation or conformance evidence and does not prove a global optimum beyond the compared designs. The literal mission E3 promise is stronger than the operational boundary the convener clarified; both readings are reported below.

## Smallest changes to the base

1. Keep `dependencies.mcp_servers` and its old version semantics. Drop normative `server.package`/`server.endpoint`; keep transport documentary in old manifests. Existing `hint` can explain setup without becoming executable authority.
2. Use existing operator-selected context/MCP packages and their profile lock when provisioning is chosen. A skill dependency does not enroll a package, mutate a profile, fetch a new range, install a plugin, or enable a server. Any native writer remains a separately governed capability; preserve its ownership model and refuse managed-home destinations.
3. Replace separate aliases and implicit identity waivers with one protected operator binding/evidence contract. It is scoped to requirement identity, consumer/project, selected target and native/managed launch; distinguish observed, operator-asserted, unknown, disabled, and conflicting states. Names remain author-chosen labels explained by each skill's hint/documentation, not a new global capability registry. One operator action can accept an enumerated batch of exact requirement identities, using the existing skill snapshot/package identity plus requirement name, with no wildcard coverage. Show each skill and hint; a new skill, changed identity or wider scope is not covered, while unchanged enumerated members remain covered. Bindings never authorize provisioning, credential routing, or bypass of source/audit/signer/system policy.
4. Evaluate evidence in the chosen launch context. Reuse validated profile/channel evidence; exclude native sources ignored by a strict channel; respect observable overrides. Preserve disabled/denied observations until effective precedence is resolved, then judge acceptance: the current positive-only OpenCode map can discard a project disable before merging a home entry. A lower-surface selector cannot evade a higher-layer disable of that same merged provider. For `any`, one positive observation or explicitly labeled accepted assertion suffices; for `all`, every selected target needs one. Unknown alone never passes. A plan is not a committed configured state. Reliance ends on operator revocation, changed bound scope/launch/requirement identity, or authoritative complete negative evidence for that same provider and selected launch. Absence from native files is not such evidence for an opaque connector. Do not add native argv/URL fingerprinting merely to N: this is named configuration/reliance, not recipe attestation; unobservable provider changes remain explicitly unverified.
5. Keep observed agents distinct from asserted acceptance in status and persistence. Evidence must be per requirement, target and selected launch: one server can be observed for Claude and asserted for Codex. Do not overload old `FoundIn` into “observed or someone approved.” **Minimal N needs no marker bump:** keep old markers as legacy native-surface observations, store explicit reliance in the governed operator-config successor, and compute stronger selected-launch status afresh. A richer portable receipt is optional only if a consumer needs that claim persisted; then count and version it separately. A scoped-verification extension/profile and old-reader behavior must be explicit, never a silent reinterpretation of legacy §6.
6. Remove the new auth-class grammar. Use native client guidance and existing env-name mechanisms only where their actual adapter capabilities suffice. Current managed HTTP declarations cannot magically turn `env_names` into headers; additional routing needs its own governed change. Keep the foreign-byte handling bound explicit, and never claim authenticated/connected or run a health probe. Raw native `command`/`argv[0]` is not an output exception: the §6 static PATH check can remain private and emit a fixed unresolved-command warning with the validated requirement and target. The implementation's current interpolation at `mcp.go:143–144` is not a normative requirement, and a bare filename is not proof of secret-free content.
7. Provision only through an operator-approved exact plan, with destination and aggregate exposure visible and changed actions invalidating approval. Evaluate the selected adapter/launch trust domain, effective passed MCP-name union, possible inheriting provider recipients and effective rollout/policy. Adding a name can widen exposure for an unchanged provider; adding a recipient can widen exposure with an unchanged name union. Both require reassessment and approval of the widened shared plan. Where complete recipients/exposure are unobservable, explicitly approve the shared launch trust domain and its visibility limit or leave the mutation unapproved; never fabricate per-server isolation. The MCP-name union is not the client's complete environment: other launcher/native inheritance remains part of that stated limit. Existing source allowlists and surfacing are necessary but not exact-plan consent. Show requiring skills for attribution, but adding a skill without changing the provider/launch plan does not renew provider WRITE consent. Per-requirement renewal belongs to opaque reliance, a separate lifecycle. Applying csk D1's no-consent HTTP exception to this dependency workflow would lose E6 credit.

## Normative homes and acceptance cases

Core §4 and the released `mcpRequirement` definition can remain unchanged for N. The new evidence/admission semantics belong in a reviewed manager extension to §6, with a governed successor of the relevant closed machine configuration if bindings use it. Manager §1 and compatibility/governance must state the opt-in, persistence authority and old-reader behavior. Launch evidence refers to environments §§5.8/7.8/8.4, without widening managed writers into native homes. Consent and metadata-only reporting require explicit behavior, not merely a new enum.

The minimum invocation choice is an explicitly opted-in scoped path at the existing project/global skill-install gate, supplied selected target/launch descriptors. Legacy invocation retains legacy native semantics. A pure requested recheck can consume an existing profile lock for its skills; that does not silently add a new fatal gate to `profile install`. Source search finds `mcp.Verify` through `install.mcpVerifier`, not `envprofile`. Automatic integration into environments §9.1/§10.1 therefore needs separately governed invocation and failure rules. A profile lock supplies evidence, not an already existing requirement-check operation. Exact input grammar and lifecycle vectors remain E7 work; no new CLI spelling is claimed.

The opted-in lane must render evidence source and grade together: **configured by name / provider identity and authentication not checked**, or **operator-asserted**. A name match establishes neither the author-intended service, endpoint control, runtime executable identity nor credential recipient. Project-file presence alone does not establish that the client trusted or activated the provider. Known rejection, disablement or exclusion defeats acceptance; unobserved activation/trust stays unknown or pending unless the defined protected scoped-reliance policy permits an explicitly asserted result. Reliance cannot grant client workspace approval or override a known refusal. Legacy §6 keeps its existing presence-plus-project-trust-warning semantics; its result is not silently upgraded. These are conditions of N's E6=2, not optional wording polish or claims about current implementation. Cryptographic enforcement of an author-selected provider identity would be an additional product requirement.

The hardened floor is the effective policy, not an invented default-deny promise. Environments §10.3 preserves absent `passable_env_names` as unbounded-with-warning under `s4-warn`, including hardened posture; hardened rejects explicit `null`. Absent becomes empty only under `s4-enforce`. Consent must therefore name the effective rollout/policy and resulting exposure. No credential values are inspected to establish those metadata facts.

Strict admission is also not a secret-free certificate. Environments §9.1 permits an exact pin/file/span secret-material waiver; schema-1 permits arbitrary bounded argument strings and HTTPS path bytes, which `contextpkg.ParseMCP:497–518` preserves. The current §2.3 row and `FormatDeclarationRows:150–175` print stdio args after admission; the row has no HTTP URL column. The §5.8 serializers at `contextmaterialize/mcp.go:244–327` also copy args/URL into generated files. A waiver changes admission, not the bytes or their disclosure/persistence authority. The proposed bounded feature keeps recommendation/evidence output metadata-only independently of admission and refuses credential-bearing provisioning under its no-use/no-store/no-forward promise. If withheld details prevent meaningful exact-plan review, the write remains unapproved. A detector miss is not a proof of safety.

Any stronger display or admission/materialization rule needs an explicit governed compatibility change wherever existing §§2.3/5.8/9.1 conflict. Unchanged delegation to that legacy lane cannot inherit an end-to-end E3 guarantee; reproducing a waived actual credential meets amended E3's zero anchor. N's E3=2 scores the proposed bounded dependency path, not all existing profile/launcher behavior. This sharpens the existing conditional boundary and keeps E7=1 rather than claiming a completed fix. Astra-02's counterexample is `$xSGO0qksc8B68V1gr6rmjfakIF3nxsK27zIAdmV0LoE`; astra-12 confirms persistence as well as display in `$lUSbVgBMWBhdEhk31UaFQqExiNO7W6fGl3S57ebwsqE`; this seat independently confirms the pinned sources in `$7xAqOx7_rd6ZhqDV7GluuciCFXbjrKXgKHwWdGcHgeQ`. The existing `f-secret-boundary` finding owns this case.

Required vector families: unchanged v5–8 grammar and documentary transport; alias collision and same-label unrelated services; explicit disabled state; native Claude excluded by strict managed launch; managed-only provider; OpenCode override; `any` observed+unknown versus all; opaque without/with assertion; assertion scoped to wrong consumer or changed requirement; assertion revocation/invalidation; source allowlist and consent remaining cumulative; incomplete publication never recorded as configured; secret-bearing foreign argv/URL never in output; malformed inputs yield metadata-only diagnostics; unsupported HTTP routing refuses or remains external setup, never a fabricated auth success.

Adversarial additions: raw native command/bare filename never echoed; legacy marker unchanged while scoped status is recomputed; a new MCP env name widens an unchanged server's potential exposure; a new recipient widens an unchanged name union; unknown recipients require the explicit shared-domain limit; hardened absent-knob behavior differs between `s4-warn` and `s4-enforce`; higher-priority OpenCode disable survives layer composition; same-name cross-kind adoption is deferred while distinct-name adoption remains possible; subdirectory remediation preserves the complete source tuple; skill recommendation updates do not imply provider updates; opted-in scoped checking is distinct from legacy install and profile installation.

Assurance vectors must also cover project-only presence with unknown client trust, a known trust refusal, allowed assertion-grade reliance without granting client approval, and same-name unrelated providers. Every result retains the identity/authentication qualifier; legacy presence and selected-launch evidence remain distinguishable.

Waiver vectors must distinguish admission from safe display and materialization: a waived credential-bearing argument is never echoed; a waived argument or URL is not copied into generated configuration by the bounded feature; withholding details never becomes implicit exact-plan consent. Current HTTP rows must not be falsely described as printing URLs, and the proposed contract must not claim a clean detector result proves all content non-sensitive.

These are proposed vectors. None was executed in this review.
