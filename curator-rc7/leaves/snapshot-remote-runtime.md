# X5 — Protect and qualify the cross-account snapshot runtime

- Owner repository: **curator-agent-launcher**. Any new pure provider-process projection in agents-management is a separately reviewed companion; the executor owns protection and qualification.
- Normative clauses: managed-home-snapshots §§6–7; CIP-0014 implementation leaves 3/6, Design §6 step 5 and `ExecRuntime_ProtectedContent`; D6; published X0 and HOST-HOME-SPEC contracts.
- Attack surface: verified immutable content becoming a writable provider runtime under a different executing account.
- Size: 5 for the common protected projection. Split genuinely different provider mechanisms before coding; retain the complete activation matrix. No platform borrows another platform's evidence.
- Cut: cross-account follow-on. X3 intake/install, same-user D4-N and common HOST-HOME helper tests do not complete this leaf.

## Acceptance

1. Publish the concrete platform mechanism before implementation. Runtime B requires the operator confirmation retained in snapshots §6; this plan and local tests do not supply it. Keep content and approved writable state/policy slots separate. If a provider must rewrite protected content, refuse that combination rather than making the snapshot mutable.
2. Construct only the admitted runtime view and covered overlays in the agent account. Preserve content/descriptor/profile identity, argv/env, typed settings and independently admitted credentials. No caller-home access, native-auth relinking, receiver seed selection, shadowing overlay or on-demand profile resolve.
3. Qualify actual start, destination login/source use, model turn and native resume for every advertised provider/build/platform/account/transport tuple. Record separate Claude, Codex and Muse evidence; retain Pi/OpenCode bounds if later advertised. Same-UID node T3b cannot authorize cross-account credentials.
4. Recheck original protected inputs and admission at restart/resume. Legitimate writes succeed only in declared slots and cannot become a new baseline. Failed integrity/protection prevents provider start; unknown liveness cannot justify a second process.

## Paired controls

| Positive control | Negative witness / intended invariant |
|---|---|
| Actual provider writes allowed state, completes its qualified lifecycle and resumes unchanged content | Protected-file rewrite, writable-ancestor replacement, link substitution or overlay shadowing is blocked/refused; original content remains intact |
| Same admitted policy and identity survive native resume | Changed descriptor/skill/support/MCP/overlay or unreadable receipt cannot relabel a baseline or select current profile |
| Admitted destination credential channel authenticates without caller-home access | Snapshot alone, source-home presence, same-user local binding or unqualified broker route cannot grant authentication |
| Correct platform protection remains effective under the executing account | A chmod-only known-vulnerable control must expose ancestor replacement to the detector; unrelated tool failure is insufficient |

Use actual production executor/account boundaries and disposable fixtures. Hash/permission inspection and model-free startup do not prove the full lifecycle. Report unverified cells and keep their capability unavailable; every supported tuple must pass the adjacent positive control.
