# X4 — Enforce snapshot capabilities and retire qualified legacy fallback

- Owner repositories: **skill-project-management** and **skill-agents-management**, as separate small commits/releases.
- Normative clauses: managed-home-snapshots §§1,6–7; CIP-0014 implementation leaf 7; D4–D6.
- Attack surface: capability selection, compatibility removal and migration claims.
- Size: 2 per repository; later activation after the exact corresponding routes qualify.

## Acceptance and paired tests

Publish minimum producer/consumer versions and measured provider/platform limits. Remove the corresponding interim copy/live-home fallback only after private snapshot, attach/resume and, where advertised, archive execution evidence is available. Unsupported or unknown required capabilities refuse explicitly; they do not select a legacy path or borrow another adapter's green result. Preserve operator state and document explicit migration of existing sessions.

A compatible supported native/spawn/hosted/remote route succeeds through its own production entrypoint. Old capability, missing receipt, unreadable baseline, protected drift and unqualified platform refuse without new provider execution or baseline replacement. A positive control for each advertised route prevents a universal refusal from satisfying migration. A bounded capability-loss plant must exercise the real selector and fail the intended gate.

Route-specific D4-N/D4-S or hosted leaves plus X1–X3 for advertised remote execution. Local migration may land independently; do not hold a corrected local route behind unrelated remote work, and do not declare D6 done from it. Paths: agents-management capability/context admission and module release metadata; project-management spawn/hosted admission, compatibility branch tests, pins/vendor and migration docs. Serialize pin/vendor changes with M5 and C5/T4; retain exact qualified commit/version evidence.
