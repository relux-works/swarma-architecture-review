## What I would examine next

1. **Runner and harness share a UID.** Evidence that reaches the host from the session runner (readiness, turn boundaries, applied receipts, exit) is agent-side evidence while the harness runs; the native-lock check is trusted only because no harness exists yet at that moment. The host spec should label which runner reports are evidence about the agent and which are trusted platform evidence (receipts and `exec.stop`), and the unpublished runner/host execution-binding proof (session host §7 q2) should say what it proves against a same-UID process.
2. **The key keeper, when it becomes a module.** Its ledger-anchored registration needs the F-17 rules (ambiguous or resurrected generations refuse) and the F-23 custody posture; `revoke` by the dispatcher only for one-shot flags; the keeper's own egress row under F-24.
3. **The bridge and the carrier.** Still architecture only: the a2a server this review ran on has no signatures and open rooms; the bridge's decision guard, `post` audience projection and the first-slice "bridge posts for the worker" authority deserve a trust review once a specification exists. ivan-network-profiles' DNS side channel applies to the bridge's carrier egress too.
4. **CIP-0002 strict project context** against the agent-account model: the hostile-repository boundary is the harness's own loading path, and a same-UID harness cannot be contained by file modes; the qualification claims per adapter should be read with F-19's lesson about same-UID executors.
5. **Remote worker join.** The invitation code is a bearer secret with no second channel by owner decision; the marketplace card is the only binding to a person. Worth a threat note when the join point is specified: who can enrol first with a stolen invitation, and what the operator sees.
6. **F-26's design input.** Compare caller release against an F-7-style record-sequence floor carried on authenticated requests before the F-10 retention gate is published; both must keep the four trust rules.
7. **Windows**, when it arrives: WFP per-UID matching, named-pipe peer identity and the absence of `setsid`/cgroup equivalents change several of the above.

Keep the accepted limits: root is trusted; a harness may read and copy its leased token; local revocation cannot erase it; v0 networking is cooperative; owner decisions D-GOALS, D-IDENTITY, D-EXECUTOR, D-PATH, D-DONOR-PROVISIONING, D-WIRE-NAMES and D-RESUME were not challenged.
