### The three release lanes

1. **Projection:** public module CI on hosted macOS and Ubuntu projects production sources into a disposable pinned board checkout. Original tests, fixtures and goldens retain their bytes. Only reviewed deterministic import/type adapters are allowed; the current tool admits only an explicit empty adapter table, so nonempty adapters need their own versioned implementation and review. Publish discovered/executed/skipped/tagged inventories, reasons and real exit results. Preserve the documented informative Linux baseline distinction; it is not Linux conformance.
2. **Consumer:** the board's private hosted Ubuntu workflow consumes the immutable public tag with no candidate replacement. It exercises real converters, `tb-sessiond` composition, CLI behavior and **whole-board CI**, including configuration, board, vendor drift, document guards, server and regression scenarios. Prototype build/vet is insufficient.
3. **Module:** public hosted macOS and Ubuntu vet/race/build plus the declared platform conformance of the extracted module. Tests requiring private board internals need a reviewed test-support disposition; silently dropping them, inventing stubs or moving their failures outside the report does not establish conformance.

Qualify deliberate mutations of projected production code, real converters and relevant guard paths: each must fail a named test, with a passing baseline. Compile failure, an unrelated failing test or absent evidence is not a mutation kill. Accept required guard-read instrumentation upstream first and pin it before relying on measured coverage. Existing live-provider and tagged opt-ins remain explicitly scoped; extraction does not claim they ran.

Keep all builds/tests on the approved hosted runners. The existing owner permission for private-board excerpts in public CI logs is distinct from artifact publication: allowlisted reports only; no private checkout, candidate archives, dependency caches or raw logs in lane artifacts. Do not expose checkout credentials to an untrusted PR-triggered job (SH §2.4; gate guide).

## C1 cutover and rollback transaction

The paired release manifest names board build, immutable module tag, wire/goal/storage versions and permitted reader/writer pairs. Keep the board build stamp in the daemon version and report the host identity separately.

Before stopping the daemon, close **every** affected-board entry path: wrapper auto-start, scheduled/recovery starts, active board runners and operator entry points. Hold and recheck exclusive state ownership throughout snapshot, binary swap, start and health verification. A late old client must not recreate the old daemon; quiescence failure postpones C1. Test all four old/new wrapper/daemon pairings in disposable environments.

This maintenance operation must account for the actual SH1 transport lifetime: today's daemon owns Claude's PTY and replacing it kills that session. Do not promise transparent re-adoption from a live PID or import SH2 runner-survival claims into this cutover. The operator schedules the resulting interruption; only the supported existing recovery behavior is claimed.

Reopen only with the paired identity and one verified writer. Before rollback opens mutable state, prove the old reader accepts **all retained records and schema versions**. Never restore an older snapshot over later accepted records. If that proof fails, keep the service closed and use the explicit repair/forward-fix path; schema incompatibility is not permission to discard evidence. The snapshot is recovery material, not a license for time travel (SH §2.6).

## SH2+ dependencies and the smallest useful integration

Contract publication, negative-vector design and host capability measurement can proceed while SH1 finishes. They must converge on the existing dispatcher socket and root launcher, not an interim board receiver, command-mode dispatcher, launch ticket or second privileged executor.

The first backend integration should be one admitted trusted local session with a selected qualified provider/transport and **no board or goal dependency**. It still needs every applicable platform gate. The later optional board adapter adds goal-revision acknowledgement/completion semantics without making a board mandatory for launch, attach, delivery, wake, stop or recovery.

Before activation, pin and qualify together:

- Session-scoped admission permit and owner lifecycle authorization; distinct account generation, physical execution and controller epoch; one-start admission cannot create successors. Every physical start uses the existing claim/effect/root-receipt path. `host_stop` authorizes stop, not restart. Expiry/revocation, cancellation and maintenance withdraw successor authority durably.
- Fresh runner-to-host authentication after UID change; FD3 remains the plan only. Current-epoch registration/readiness precedes delivery. Controller-only re-adoption retains the execution ID; replacing an execution needs confirmed account-wide absence. Native-lock checks and harness-surface digests remain independent of compatibility.
- Published process-fate rows and platform evidence. A detached process or `setsid` is not a survival guarantee; retain the dispatcher daemon-instance writer fence. The runner, not the host service, owns the PTY/private app-server and broker client.
- Durable per-record intent/in-flight markers, bounded unlocked I/O, unknown receipt reconciliation and protected service-storage capacity. Lost or unreadable evidence cannot release capacity, replay unknown control, fabricate an applied receipt or reopen delivery. Authorized status/stop stays reachable within the existing recovery limits.
- Explicit goal-client and optional adapter contracts before enabling them; current D-GOALS remains caller/board authorship. Defer agent self-goals. Resolve the reboot requester before enabling that restart path; choosing one minimal configured owner need not design multiple competing recovery writers.

The hosted-launch r6 material is input only: harvest strict validation, exact process projection and credential-free record requirements. Its task-board receiver/reservation service, payload and adapter schemas are superseded, not an implementation shortcut (`docs/inputs/hosted-launch-contract-r6.md:1–5,22–30`).

## Effort, risks and deliberate exclusions

The spec's October 9 planning baseline is six SH1 landings F/O/G/X/Y/Z: **18–24 serial landing-hours clean, 60–72 with one rework each**, plus C1's maintenance slot. These are historical assumptions, not elapsed-time promises or a fresh estimate that ignores work already done. Re-estimate the remaining F/seam/release work after the pinned graph proof and include measured CI latency only where it was not already included. The observed prototype macOS projection job took about 34 minutes; new converter and module conformance work may change that. Two shared-host runs were the old capacity assumption; runner availability and review/landing capacity determine calendar time. The SH2 estimate of 15–25 cross-module changes remains low-confidence until its joint contracts and current cycle-3 remedies are published (SH §4).

Stop or narrow the extraction if the representative graph fails, parity needs unexplained test edits, a converter bypasses local policy, provenance is incomplete, the source freeze has no single integrator, required evidence is missing or consumer/schema compatibility cannot be proven. Preserve the working board dependency until those gates pass. Escalate a changed calendar/ownership decision explicitly; do not silently reinterpret it.

Do not build a second task-board server, a universal plugin bus, a new goal ledger, a parallel legacy hosted receiver, a second launch path, automatic resume fallback or generic migration machinery to make SH1 look like the target platform. The useful first result is a tested public library consumed by the existing board. The useful next result is a separately qualified platform backend with one clear owner for each effect.
